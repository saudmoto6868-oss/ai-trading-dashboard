## 1) الهدف من المحضر

توحيد صورة واحدة للفريق عن:

1. ماذا يحدث في سوق أدوات التداول المؤتمتة والـ AI الآن.  
2. أنواع الأدوات الحقيقية (لا الأسماء التسويقية فقط).  
3. كيف تعمل كل فئة من الداخل.  
4. الإيجابيات والسلبيات بصراحة.  
5. ماذا يقول القياس الجاد (باك تست / paper / لايف / أبحاث) مقابل إعلانات X.  
6. كيف نقرأ السوشيال من غير ما نشتري الرقم.  
7. ترتيب عملي لما نلمسه أولاً وما نرفضه.  
8. مهام واضحة بعد القراءة.

## 2) الصورة الكبيرة والسياق

### 2.1 الانتقال الجاري

| من (الجيل السابق الشائع) | إلى (ما يُدفع في 2025–2026) |
|--------------------------|------------------------------|
| بوت إشارة / Grid / DCA فقط | **Agentic trading**: وكيل يبحث ويخطط وأحياناً ينفّذ |
| مؤشر + تنبيه على الشارت | حسابات بروكر للوكلاء + MCP/Skills + حوكمة |
| «اشترِ بوت AI يربح» | واقع القياس: **البناء سهل · الحافة صعبة · التكرار ضعيف** |
| سكربت على VPS | وكيل محادثة متصل بحساب حقيقي بحدود |

### 2.2 الجملة المحورية

**الأتمتة تنفّذ edge موجود؛ نادراً ما تخلق edge من كلمة «AI» على المنتج.**

الـ LLM قوي في: كتابة كود، تلخيص أخبار، صياغة خطة، مراقبة قواعد.  
الـ LLM ضعيف كمتداول مستقل ثابت الربح حسب أغلب القياس الحي المتاح علناً حتى تاريخ هذا المحضر.

### 2.3 ثلاثة أشياء تُسمّى كلها «وكيل» وهي مختلفة

| المسمّى | الواقع |
|---------|--------|
| مساعد داخل التطبيق | يجيب ويجهّز أمراً؛ الإنسان يضغط |
| موصل MCP | موديل خارجي يقرأ الحساب ويقترح أو ينفّذ حسب الإعداد |
| وكيل قائم 24/7 | يعمل على قواعد/إطار من غير طلب كل مرة |

خلط الثلاثة في نقاش الفريق ممنوع؛ حدّدوا أي تعريف تقصدون.

## 3) قاموس مصطلحات سريع

| مصطلح | معنى عملي |
|--------|-----------|
| **Bot (قواعد)** | شروط مبرمجة مسبقاً تنفّذ أوتوماتيك |
| **Agent** | نظام يلاحظ، يستنتج، يستخدم أدوات، ويتصرف بدرجة استقلالية |
| **MCP** | بروتوكول/طبقة أدوات تربط الموديل بخدمات (منها حساب تداول) |
| **Paper** | تنفيذ على أسعار حقيقية بلا رأس مال حقيقي (أو بمحاكاة) |
| **Live** | فلوس حقيقية |
| **Backtest** | إعادة تمثيل القواعد على تاريخ ماضٍ |
| **Overfitting** | قواعد «ممتازة» على الماضي فقط لأنها حفظت الضجيج |
| **Kill switch** | إيقاف فوري لكل تداول آلي |
| **Edge** | أفضلية إحصائية متوقعة بعد التكاليف |
| **AgentFi** | وكلاء مالية على سلاسل/محافظ لامركزية |

## 4) خريطة أنواع الأدوات (A–G)

| # | النوع | الفكرة الجوهرية | أمثلة تُذكر في السوق (ليست توصية) |
|---|--------|-----------------|-----------------------------------|
| **A** | بوت قواعد كلاسيكي | Grid، DCA، تقاطع متوسطات، شروط ثابتة | 3Commas، Pionex، Cryptohopper، Freqtrade |
| **B** | منصة استراتيجيات قابلة للأتمتة | بناء قواعد (واجهة أو لغة) → باك تست → تشغيل آلي للقواعد | Composer by SoFi |
| **C** | وكيل على البروكر | موديل + حساب حقيقي عبر MCP/تكامل رسمي | Robinhood Agentic، Coinbase for Agents، Public، Gemini، IBKR، Webull، eToro، moomoo |
| **D** | Multi-agent desk | أدوار متعددة قبل الأمر | TradingAgents وأطر مفتوحة مشابهة |
| **E** | بطاقة إشارة + تنفيذ | خطة كاملة في كارت → زر تنفيذ | منصات كريبتو/perps على السوشيال |
| **F** | AgentFi / on-chain | وكيل + محفظة + بروتوكولات | مشاريع AgentFi، محافظ وكيلية، perps on-chain |
| **G** | بنية مفتوحة | محرك تنفيذ، بيانات، بوت — أنت تبني الـ edge | NautilusTrader، OpenBB، Freqtrade، أطر multi-agent |

**ملاحظة تصنيف:** فيديو «AI trading tool» على X غالباً = **A+E** أو **C** بواجهة جميلة.

## 5) آلية عمل كل فئة بالتفصيل

### 5.1 النوع A — بوت القواعد

**التدفق:**

```
بيانات سوق (سعر/حجم/مؤشر)
    → تقييم شروط مبرمجة (لو السعر < X و RSI < 30 …)
    → حساب حجم
    → إرسال أمر لبورصة/بروكر
    → إدارة خروج (TP/SL/trailing) بنفس القواعد
```

**خصائص:**

- زمن قرار بالميلي ثانية إلى الثواني.  
- تكلفة تشغيل منخفضة نسبياً.  
- لا يغيّر رأيه بسبب «خبر» ما لم تبرمجوه.  
- يفشل حين يتغيّر نظام السوق (مثلاً Grid في ترند قوي بلا حماية).

**متى يناسب:** سوق أو أصل له سلوك متكرر معروف؛ قواعد مختبرة؛ منضبطة الرسوم.

### 5.2 النوع B — قواعد يبنيها AI ثم تُنفَّذ آلياً

**التدفق:**

```
فكرة بالكلام العادي أو بالواجهة
    → AI / المنصة تصيغ قواعد صريحة (لو… إذن… أوزان… فلاتر)
    → باك تست على تاريخ
    → المستخدم يراجع ويعدّل
    → تفعيل: إعادة توازن/أوامر حسب القواعد فقط
```

**خصائص:**

- الشفافية أعلى من وكيل حر: يمكن قراءة القاعدة.  
- الـ AI ليس بالضرورة من يقرّر لحظة بلحظة بعد التفعيل.  
- خطر المجتمع: استراتيجيات عامة مُحسَّنة للعرض لا للـ out-of-sample.

**Composer/SoFi (كسياق سوق):** يُسوَّق كمسار من الفكرة → الاختبار → التنفيذ بقواعد، مع تمييز صريح نسبياً عن وكيل يقرّر باستمرار.

### 5.3 النوع C — وكيل البروكر

**التدفق:**

```
مستخدم يربط موديل (Claude / ChatGPT / Grok / …)
    → أدوات MCP: رصيد، أوامر، أسعار، بحث
    → الموديل يخطط
    → إما: يطلب موافقة بشرية على كل أمر
       أو: ينفّذ داخل سقف مُعد مسبقاً
```

**جدول أنماط الموافقة:**

| النمط | الوصف | مستوى الخطر التشغيلي |
|-------|--------|----------------------|
| موافقة إلزامية لكل أمر | كوبايلوت | أقل |
| موافقة اختيارية / يمكن تعطيلها | شبه أوتونومي | متوسط–مرتفع |
| تنفيذ مباشر ضمن tool permissions | أوتونومي محدود | مرتفع إن بلا سقف إضافي |

**خصائص:**

- راحة عالية للمستخدم غير التقني.  
- تكلفة توكنات + احتمال هلوسة أرقام.  
- أمان المفاتيح/OAuth حرج.  
- الأداء الربحي **غير مضمون** من اسم البروكر.

### 5.4 النوع D — Multi-agent

**التدفق النموذجي:**

```
Scout/بيانات → Analyst (أطروحة + ثقة)
    → Risk (رفض أو تقليل حجم)
    → Verifier (يفحص الأرقام ضد المصدر الخام)   [موصى به بقوة]
    → Executor أو Human gate
```

**المبدأ الذهبي المسجّل في المحضر:**

> الموديل الذي يريد فتح الصفقة لا يُسمح له أن يكون الحكم الأخير على صحة أرقامه.

**خصائص:**

- أفضل للحوكمة والتفسير.  
- تكلفة أعلى ووقت أطول لكل قرار.  
- إن كانت الوكلاء مترابطة بنفس البيانات المتحيزة، تفشل معاً.

### 5.5 النوع E — بطاقة إشارة + تنفيذ

**التدفق:**

```
ماسح أسواق → توليد بطاقة:
  اتجاه | دخول | وقف | أهداف | رافعة مقترحة | سبب نصّي
    → المستخدم يضغط Execute
    → تحميل الخطة في منصة التداول / المحفظة
```

**خصائص:**

- أفضل UX تسويقي على X.  
- أصعب فئة لإثبات edge مستقل (من يقيس كل البطاقات؟).  
- السبب النصّي قد يكون مقنعاً لغوياً وخاطئاً رقمياً.

### 5.6 النوع F — AgentFi / on-chain

**التدفق:**

```
إعداد استراتيجية / برومبت
    → صلاحيات محفظة (حدود إنفاق، whitelist)
    → تنفيذ على perps / DEX / prediction markets
    → مراقبة on-chain
```

**خصائص:**

- شفافية سلسلة محتملة.  
- مخاطر عقد ذكي + مفاتيح + تصيّد («أفضل سعر» فخ للوكلاء).  
- نضج متفاوت جداً بين المشاريع.

### 5.7 النوع G — بنية مفتوحة

**أمثلة أدوار المكوّنات:**

| مكوّن | دور |
|--------|-----|
| NautilusTrader وأشباهه | محرك: نفس الكود باك تست ولايف قدر الإمكان |
| OpenBB | طبقة بيانات وبحث |
| Freqtrade | بوت كريبتو + باك تست شائع |
| أطر multi-agent | تنظيم أدوار القرار |

**خصائص:** تحكم كامل · صفر ضمان ربح · أنت مسؤول عن السيرفر والمفاتيح والقياس.

## 6) ترندات الفترة الأخيرة — تفصيل

### 6.1 حسابات وكيلية عند بروكرز

- إطلاقات/توسعات عند أسماء كبيرة (Robinhood، Coinbase، eToro، Webull، Gemini، …).  
- الهدف المنتج: تقليل الحاجز لملايين المستخدمين.  
- لا يساوي: «ثبتنا أن الوكيل يغلب السوق».

### 6.2 MCP وSkills

- طبقة توصيل معيارية نسبياً بين الموديلات والحسابات.  
- حجم تداول وكلاء على منصات مثل Coinbase for Agents يُذكر كرقم نشاط (تبنّي) لا كدليل alpha.

### 6.3 بوت vs وكيل — الخلط التسويقي

كثير من المنتجات «AI bot» = قواعد Grid/DCA + شات يشرح. الفريق يصنّف بالمحتوى لا بالشعار.

### 6.4 Multi-agent كمودة معمارية

شائع على GitHub وX. القيمة الحقيقية في **بوابة الرفض** لا في عدد الوكلاء على الداشبورد.

### 6.5 Open-source

قوائم «كنز GitHub» تنتشر (محركات، بيانات، بوتات). مفيدة كبنية. الربح منفصل.

### 6.6 Prompt → تنفيذ (ميمز / perps)

قصص «من عشرات الدولارات لألاف في أسبوع» شائعة. غالباً: رافعة، عينة صغيرة، اختيار لحظة، عدم احتساب الخسائر اللاحقة.

### 6.7 الحوكمة

Kill switch، سقف صفقة/يوم، موافقة بشرية، سجل قرارات — هذا ما تكرّره المؤسسات والتحليل الجاد أكثر من «نسبة فوز 90%».

### 6.8 AgentFi

نمو اهتمام وTVL في تقارير القطاع؛ التجزئة كثيرة؛ الجودة غير موحّدة.

## 7) إيجابيات وسلبيات — نسخة معمّقة

### 7.1 النوع A

**إيجابيات:** بساطة · تكلفة منخفضة · باك تست مفهوم · سلوك متوقع.  
**سلبيات:** هشاشة النظام · لا يتكيّف مع خبر مفاجئ ما لم يُبرمج · منافسة عالية على أنماط معروفة.

### 7.2 النوع B

**إيجابيات:** مسار منضبط (اختبر ثم شغّل) · قواعد قابلة للمراجعة · AI يسرّع التصميم.  
**سلبيات:** خداع الباك تست الجماعي · رافعة مخفية في الاستراتيجيات الشائعة · إحساس زائف بالأمان من الرسم البياني التاريخي.

### 7.3 النوع C

**إيجابيات:** وصول سريع · لغة طبيعية · تكامل رسمي يقلّل بعض أخطاء الربط اليدوي.  
**سلبيات:** هلوسة · تكلفة · قرارات غير متكررة · خطر صلاحيات واسعة · دليل ربح عام ضعيف.

### 7.4 النوع D

**إيجابيات:** فصل الاهتمامات · قابلية تفسير · مكان طبيعي لمدقّق.  
**سلبيات:** تعقيد · تكلفة · بطء · تحيز مشترك إن لم تُستقل مصادر التحقق.

### 7.5 النوع E

**إيجابيات:** وضوح الخطة للمستخدم · سرعة قرار بشري.  
**سلبيات:** أعتم صندوقاً من ناحية الإحصاء · حافز تسويق قوي · صعوبة التدقيق الخارجي.

### 7.6 النوع F

**إيجابيات:** برمجة أموال 24/7 · قابلية تركيب بروتوكولات.  
**سلبيات:** أمن · تصيّد موجّه للوكلاء · سيولة · عقود.

### 7.7 النوع G

**إيجابيات:** ملكية كاملة · تدقيق · لا قفل بائع.  
**سلبيات:** عبء تشغيلي · أخطاء هندسية = خسائر · لا edge افتراضي.

## 8) باك تست · Paper · لايف · أبحاث — التفصيل الكامل للفريق

### 8.1 ماذا يعني كل مستوى قياس

| المستوى | ماذا يقيس | ماذا لا يقيس |
|---------|-----------|--------------|
| Backtest | هل القواعد نجحت على ماضٍ معيّن | الانزلاق الحقيقي، الأعطال، تغيّر النظام بالكامل |
| Paper | قرارات على أسعار حية بلا رأس مال (حسب جودة المحاكاة) | ضغط العاطفة أحياناً؛ بعض تكاليف التنفيذ |
| Live صغير | الواقع تحت حجم محدود | الأداء تحت حجم كبير |
| Live كبير | الواقع الأشمل | — |

### 8.2 نتائج متكررة من القياس العام (حتى تاريخ المحضر)

1. **مواسم موحّدة لموديلات LLM** (رأس مال ورقي موحّد، آلاف الصفقات عبر مواسم): نسبة مواسم رابحة أقل من النصف تقريباً في تقارير عامة؛ **عدم استقرار الترتيب** بين موسم وآخر.  
2. **أبحاث agents ذاتية**: الذكاء العام لا يترجم تلقائياً لتفوق تداولي؛ إدارة المخاطرة نقطة ضعف متكررة.  
3. **معايير متعددة المراحل على كريبتو**: فجوة باك تست→paper→live؛ طرق ML تقليدية قد تبدو أفضل على التاريخ من LLM/agents في بعض الإعدادات؛ زمن قرار الوكلاء أبطأ وانزلاق أكبر في قياسات.  
4. **Postmortem عملي**: بوت يُبنى بسرعة؛ لا يظهر edge؛ فاتورة API حقيقية؛ باج «سجّل قبل ما يتأكد التنفيذ» خطر على اللايف.  
5. **لوحات شفافة**: متوسطات تحت السوق تظهر؛ النشر الأمين يشمل الفشل.

### 8.3 باك تست كتالوجات الاستراتيجيات (مثال نمط Composer)

- تظهر عوائد سنوية وSharpe مرتفعة وdrawdowns كبيرة أحياناً.  
- أنماط شائعة: رافعة على مؤشرات، تناوب، mean-reversion — حساسة للفترة.  
- **قاعدة الفريق:** أي استراتيجية مجتمعية تُعامل كفرضية حتى تثبت out-of-sample وpaper بتكاليفكم.

### 8.4 لماذا ينهار الأداء من المحاكاة إلى الواقع

1. رسوم كل طرفي الصفقة  
2. انزلاق وسيولة  
3. نافذة اختبار قصيرة أو نظام واحد (صعود طويل مثلاً)  
4. رافعة تضخّم  
5. تأخير قرار LLM مقابل حركة السعر  
6. تعديل الاستراتيجية بعد رؤية الماضي (overfitting بشري)  
7. أعطال مفاتيح/API/إعادة اتصال  

### 8.5 الحد الأدنى المقبول لقياس أداة قبل «جدّية»

- تعريف قواعد أو سياسة قرار مكتوبة.  
- تكاليف صريحة في الاختبار.  
- فترة out-of-sample أو paper ممتد.  
- سجل صفقات قابل للمراجعة.  
- شرط إيقاف (خسارة يومية / تعطّل بيانات).

## 10) الحافة — أين ممكن وأين لا

| الادّعاء | موقف المحضر |
|----------|----------------|
| الموديل الأذكى = المتداول الأفضل | مرفوض كقاعدة؛ القياس لا يدعم التكرار |
| الأتمتة تخلق الربح | الأتمتة تنفّذ؛ الـ edge منفصل |
| كثرة الوكلاء ترفع الربح | ترفع إمكانية الحوكمة لا الضمان |
| باك تست جميل = جاهز للايف | غير كافٍ |
| بروكر كبير يقدّم وكيلاً = الوكيل مربح | خلط بين منتج وأداء |
| الاستدامة الحقيقية الأقرب | قواعد بسيطة + مخاطرة + نظام مناسب + مراجعة؛ AI للبناء والمراقبة والمساعدة |

## 11) الترتيب العملي (إلزامي كمرجع نقاش)

من **الأكثر انضباطاً** إلى **الأكثر ضجيجاً**:

1. **محرك قواعد + باك تست جاد + paper + حدود**  
2. **AI يصيغ القواعد → موافقة بشرية → تشغيل القواعد آلياً**  
3. **كوبايلوت بروكر (موافقة كل صفقة)**  
4. **Multi-agent + بوابة ريسك + مدقّق أرقام**  
5. **وكيل شبه مستقل بسقف يومي/صفقة + kill switch**  
6. **بطاقة إشارة / تليجرام / قصة أسبوع على X**  

أي اقتراح جديد من الفريق يُوضَع على هذا السلم صراحة في التعليق.

## 15) مبادئ عمل مستخرجة (تُحترم أثناء الشغل على هذا المحضر)

7. صنّفوا قبل ما تعجبوا.  
8. سجّلوا الفشل كما تسجّلون النجاح.
